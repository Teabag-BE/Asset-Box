## M1. MVP 완성 (5/27 ~ 6/5)

목표: **한 사이클이 끊김 없이 돈다.**
"TA가 가입 → 에셋 게시글 작성 → 마이페이지에서 본인 포트폴리오 확인 → 요청 게시판의 요청 한 건 확인" 까지.

### M1에 들어가는 기능 (MUST)

- User: 회원가입(Form), 로그인(JWT), `/me`, 프로필 조회, `name`/`major` 입력, 이메일 화이트리스트
- File: 통합 도메인 — 업로드/조회/메타/삭제. `domainType` + `domainId` 기준. 대표 썸네일·프로필·요청 참고 이미지는 URL 보존
- Post: 작성/조회/목록(페이지네이션), 카테고리 단일 참조, 좋아요, `**linkedRequestId` 필드 (요청과 연결)**
- Request: 작성/조회/목록, 3단계 상태(`REQUESTED` → `IN_PROGRESS` → `COMPLETED`), **TA 본인이 수락(assign)**, 업로드 시 자동 COMPLETED
- Comment: Post / Request 양쪽 댓글 (대댓글은 v1으로 미뤄도 OK)
- Category: roots / children 두 API, 시드 데이터
- Tag: findOrCreate, 게시글에 붙이기
- DM: 이슈 #12는 Message 엔티티/Repository 기본 골격. Service/Controller, 시스템 발신자, WebSocket은 후속 이슈
- Infra: docker-compose dev 환경, GitHub Actions 빌드, CORS, GlobalExceptionHandler

> **JWT (JSON Web Token)** = 로그인 후 받는 출입증. 위변조 못 하게 서명되어 있음.
> **CRUD** = Create / Read / Update / Delete. 자원 4가지 기본 동작.
> **REST 폴링(polling)** = 클라이언트가 5초마다 API를 다시 호출해서 새로운 게 있나 확인. 실시간은 아니지만 단순함.
> **CORS (Cross-Origin Resource Sharing)** = 프론트가 다른 도메인의 백엔드 API를 부를 수 있게 허용하는 규칙. 안 풀면 브라우저가 차단.
> **시드(seed) 데이터** = 앱이 부팅하자마자 DB에 깔리는 기본 데이터. 예: 카테고리 대분류, 관리자 계정.
> **이메일 화이트리스트** = 가입 가능한 이메일 도메인/주소 목록. 외부 가입 차단용.

> **통합 테스트(Integration Test)** = 도메인 여러 개를 실제로 연결해 한 시나리오를 끝까지 돌려보는 것. 단위 테스트(unit test)는 한 메서드만 보지만, 통합 테스트는 "가입 → 로그인 → 게시글 작성 → 다운로드" 같은 사용자 흐름을 본다.
> **MVP 락(lock)** = "여기까진 이제 안 바꿈." 더 추가 기능 욕심 멈추고, 있는 거 안정화에만 집중하는 시점.
> **P0 버그** = Priority 0. 즉시 픽스해야 사이클이 돌아가는 치명적 버그.
> **엔티티(Entity)** = JPA의 `@Entity` 클래스. DB 테이블 한 줄에 대응되는 자바 객체.
> **Repository** = DB와 대화하는 인터페이스. `findById`, `save` 등 메서드 제공.
> **컨트롤러(Controller)** = HTTP 요청을 받아서 적절한 서비스로 넘기는 입구. `@RestController`.

> 6/6 ~ 6/14: 핵심 기능 구현 + 6/14 EOD 베타 배포.
> 6/15 ~ 6/16: 배포 후 모니터링과 핫픽스.

### M2에 추가되는 기능

- **요청 게시판 완성 흐름**:
  - Unity/Unreal 반이 요청 작성 → TA가 본인이 수락(assign) → 작업 → 에셋 게시글 작성 시 `linkedRequestId` 박으면 **자동 COMPLETED** (GitHub Issue 닫히듯)
  - 상태 변경 시 요청자에게 시스템 DM 자동 발송
- Post/Request: 대댓글, 좋아요 토글, 인기 태그 캐시
- File: 메타 조회, 삭제(soft)
- Search: `?tag=` `?keyword=` `?categoryId=` 검색, 정렬(최신/인기)
- DM: **WebSocket 전환**, 안 읽은 수, 실시간 푸시
- Admin: 운영자가 모든 게시글/유저/메시지/요청 흐름을 **모니터링** (분쟁 처리·강제 삭제 같은 강한 권한은 본 프로젝트 범위 외)
- Feedback: 피드백 보내기 + 어드민 조회
- Infra: Prometheus, 헬스체크, 운영 프로파일, 도커 컴포즈 통합

> **캐시(Cache)** = 자주 쓰는 결과를 임시로 저장해두고 다시 계산 안 하는 것. 메모(Memo)와 비슷. Caffeine은 자바용 인메모리 캐시 라이브러리.
> **Prometheus** = 백엔드 메트릭(요청 수, 응답시간 등)을 주기적으로 긁어서 저장하는 모니터링 도구.
> **헬스체크(Health check)** = "살아 있냐?" 확인용 가벼운 엔드포인트. `/actuator/health`. 운영자가 죽었나 살았나 자동 감시.
> **운영 프로파일(prod profile)** = 운영 환경용 설정 묶음. dev는 H2(가벼운 임시 DB), prod는 MySQL.
> **WebSocket** = 카톡처럼 한 번 연결한 뒤 양방향 즉시 푸시 가능한 통신.

> **회귀 테스트(Regression Test)** = "예전에 잘 되던 게 새 코드 때문에 망가지지 않았나" 다시 돌려보는 테스트. 통합 테스트와 비슷하지만 목적은 "퇴보(regression) 막기".
> **베타(beta) 배포** = 정식 출시 전, 일부 사용자(여기선 TA반·Unity·Unreal 반)에게 먼저 공개해서 피드백 받는 단계.
> **리허설(rehearsal)** = 본 공연(배포) 전에 똑같이 한번 해보는 예행연습.

| 6/16 (화) | 모니터링 지속, 최종 핫픽스, **회고 미팅**(KPT), v1.1 백로그, 최종 보고서 + 발표 자료 + 데모 영상 |


> **트리아주(Triage)** = 응급실에서 부상자 중증도 분류하듯, 이슈를 P0(지금 당장)/P1(이번 주)/P2(나중에)로 나눠 우선순위 정하는 작업.
> **핫픽스(Hotfix)** = 운영 중에 발견된 치명적 버그를 빨리 고쳐 배포하는 긴급 패치.
> **KPT 회고** = Keep(유지)·Problem(문제)·Try(시도) 세 칸으로 정리하는 회고법.
> **백로그(Backlog)** = "다음에 할 일 목록." 우선순위는 정해두되 지금은 안 함.

**Gate**: 6/16 EOD에 회고록 + v1.1 백로그 + 데모 영상이 `01_planning/회고/` 에 들어간다.

## 데일리 / 위클리 의식 (rituals)

> **의식(ritual)** = 정기적으로 같은 시간에 같은 방식으로 하는 일. 별것 아닌 것 같아도 머지 충돌의 99%는 "옆 사람이 뭐 하는지 모르는" 데서 옴.


| 의식                         | 빈도       | 시간  | 형식                                                                           |
| -------------------------- | -------- | --- | ---------------------------------------------------------------------------- |
| 데일리 스탠드업                   | 매일 (월~금) | 10분 | Slack 스레드 — 어제 한 것 / 오늘 할 것 / 막힌 것                                           |
| 위클리 동기화                    | 매주 월     | 30분 | 화상 — 이번 주 게이트, 컨트랙트 변경 안건                                                    |
| 통합 테스트 데이                  | M1·M2 끝  | 반나절 | 다같이 모여 한 사이클 돌리기                                                             |
| 코드 리뷰 + Red Team Review 데이 | 매주 금     | 1h  | 이번 주 PR 점검 + 각자 10분씩 본인 도메인 설명, 듣는 팀원은 **red team** 방식으로 공격적으로 질문 (별도 문서 참고) |
| 회고 (KPT)                   | M3 마지막 주 | 1h  | Keep / Problem / Try                                                         |


> **스탠드업(Stand-up)** = 짧게 서서 진행하는 미팅(원래 어원). 길어지지 말라는 의미. Slack 글로 대신해도 OK.
> **머지(Merge) 충돌** = 두 사람이 같은 줄을 다르게 고쳤을 때 Git이 "어느 쪽이 맞아?" 라며 자동 병합을 못 하고 멈추는 상황.
> **Red Team Review** = 매주 1회 각 담당자가 자기 도메인을 10분간 설명하고, 다른 팀원이 공격자 관점으로 질문하는 검증 미팅. 상세 진행 방식은 `[../08_collaboration/04_Red_Team_Review.md](../08_collaboration/04_Red_Team_Review.md)` 참고.

| 리스크                       | 발생 가능성 | 영향  | 완충안                                          |
