## 코드 리뷰 + Red Team Review 데이 (매주 금 1h)

전반부 — **코드 리뷰**:

- 그 주에 머지 안 된 PR 다같이 보기 (1인당 3분 발표)
- 사소한 컨벤션 PR은 그 자리에서 머지
- 큰 PR은 리뷰어 추가 지정

후반부 — **Red Team Review** (2~3명씩 발표):

- 발표자는 본인 도메인을 10분간 설명
- 다른 팀원은 공격자(red team) 관점에서 질문 — "왜 이런 구조?", "예외 처리는?", "권한 충돌은?"
- 발견된 문제는 GitHub Issue 로 등록 + 이후 PR로 해결
- 상세 진행 방식: `[../08_collaboration/04_Red_Team_Review.md](../08_collaboration/04_Red_Team_Review.md)`

> **Red Team** = "공격 팀". 본인 도메인을 방어하는 입장에서 약점을 미리 찾는 학습 효과.

## 개인 일일 체크리스트 (저녁 퇴근 전 1분)

- 오늘 작성한 코드는 push 했다
- 빌드(`./gradlew clean compileJava`) 깨지지 않는다
- 본인 PR에 24시간 이상 묵힌 리뷰 코멘트가 없다
- 컨트랙트(API/ERD) 변경했다면 `04_api/` 또는 `03_erd/` 도 갱신했다
- 데일리 스탠드업 작성했다

## PR 머지 전 체크리스트

- `./gradlew clean compileJava test` 통과 — *빌드(코드 컴파일)와 테스트가 안 깨지는지*
- 본인 도메인의 핵심 시나리오에 대한 테스트(IT 또는 단위) 1개 이상 추가
  - **IT (Integration Test)** = 통합 테스트. 도메인 여러 개 묶어서 한 시나리오 끝까지 실행
  - **단위 테스트(Unit Test)** = 메서드 하나만 좁게 검증
- **남의 도메인 엔티티를 직접 import 하지 않았다** (서비스 호출 또는 ID만 사용)
- DTO 응답이 `ApiResponse<T>` 로 감싸져 있다
  - **DTO (Data Transfer Object)** = 계층 사이 데이터 전달용 객체. 엔티티 직노출 X
- 비즈니스 예외는 `BusinessException` + `ErrorCode` enum 사용 (Real 표준)
- DDL/엔티티 변경이 있으면 Infra 리뷰어 추가
  - **DDL** = Data Definition Language. CREATE TABLE 같은 스키마 변경
- API 변경이 있으면 `04_api/` 도 같은 PR에서 수정
- PR 설명에 "왜" 한 줄, "어떻게" 한 줄, "테스트 방법" 한 줄
