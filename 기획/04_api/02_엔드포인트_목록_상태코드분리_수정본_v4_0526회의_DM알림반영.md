## 0. 2026-05-26 TA 전체 회의 반영 핵심 결정

### 인증 / 회원가입

- 로그인 방식은 **Form + OAuth2(Google, Naver)** 를 병행한다.
- 구현 우선순위는 **Form → Google → Naver** 순서로 둔다.
- Kakao는 이메일 매칭이 복잡해질 수 있으므로 v1에서는 예외 케이스로 보고 **Form 회원가입을 권장**한다.
- 가입 가능 여부는 **이메일 화이트리스트**로 제한한다.
- Form 회원가입 시 `name`, `nickname`, `major`를 받는다.
- User의 `bio`는 제거하고, 가입/로그인 방식은 `provider=LOCAL/GOOGLE/NAVER`로 저장한다.
- `major == null`인 사용자는 로그인 후 **내 정보 보완 페이지로 리다이렉트**하고, 보완 전까지 다른 페이지 이동을 제한한다.
- 가입 이후 일반 유저는 `name`, `major`를 직접 수정할 수 없다. 수정은 관리자 정책 영역으로 둔다.
- Redis, 분산락은 v1 이후로 보류한다.
- `teamId` 기반 필터와 `team_id` 컬럼은 MVP에서 제외한다. 팀 기능이 필요해지면 `teams` 테이블과 함께 v1.1에서 재검토한다.

### 권한 / 운영

- 일반 에셋 게시글은 저작권 및 내부 공유 정책 때문에 **비회원 열람 불가**로 변경한다.
- 권한 변경 같은 운영 작업은 **SUPER_ADMIN/root 전용**으로 둔다.
- **분쟁 처리·글 강제 삭제·메시지 강제 열람 등 강한 운영 권한은 본 프로젝트 범위 밖**으로 본다. Admin은 **모니터링과 통계 조회 중심**으로만 둔다.
- 요청 게시판 흐름은 **요청자와 Assignee(TA) 중심**으로 설계한다. **어드민 개입 없음.**

### 파일 정책

- 파일 도메인은 에셋 파일뿐 아니라 **게시글 썸네일, 프로필 이미지, 요청 게시판 참고 썸네일**까지 공통으로 관리한다.
- 파일 업로드 요청은 각 도메인 API에서 multipart로 받고, 실제 저장/검증/메타데이터 관리는 File 도메인 서비스에 위임한다.
- 파일 다운로드/이미지 조회도 로그인 사용자에게만 허용한다.
- 파일 메타데이터는 `ownerId`가 아니라 `resourceType` + `resourceId`로 연결 대상을 표현한다. 예: `USER`, `POST`, `REQUEST`.
- 다운로드 로그/파일 통계는 MVP 범위에서 제외하고, 추후 Analytics/Audit 또는 운영 모니터링 범위에서 재검토한다.

### 요청 게시판 상태 흐름 (2026-05-26 TA 전체 회의 반영)

요청 게시판은 이제 **Unity/Unreal 반이 필요한 에셋을 올리고, TA 반 사람이 보고 본인이 선택해서 수락하는 흐름**으로 단순화한다.

상태는 3개로 통일한다.

```text
REQUESTED(요청됨) → IN_PROGRESS(제작중 / TA 승낙) → COMPLETED(완료)
```

흐름:

1. **요청 작성** — Unity/Unreal 반(요청자)이 `POST /api/requests`로 필요한 에셋 요청을 올린다. 생성 즉시 `status=REQUESTED`.
2. **작성 전 확인 팝업** — 요청 작성 버튼을 누를 때 프론트에서 “요청은 작성 후 취소할 수 없습니다. 등록하시겠습니까?” 확인 팝업을 띄운다.
3. **TA 수락** — TA 반 사용자(USER 권한)가 요청 목록을 보고 본인이 맡을 요청을 선택한다. `PATCH /api/requests/{id}/assign` 호출 시 `assigneeId=현재 사용자`, `status=IN_PROGRESS`. 이때 요청자에게 시스템 DM으로 “{assigneeNickname}님이 {requesterNickname}님의 요청을 수락해서 제작중입니다.” 알림을 보낸다.
4. **작업** — assignee가 에셋을 제작한다.
5. **완료 — 자동 전환** — assignee가 에셋 게시글을 작성할 때 `POST /api/posts`의 `data.linkedRequestId`에 요청 ID를 넣는다. 게시글 저장과 동시에 해당 요청의 `linkedPostId`가 설정되고 `status=COMPLETED`로 자동 전환된다. 이때 요청자에게 시스템 DM으로 “{assigneeNickname}님이 {requesterNickname}님의 요청 제작을 완료했습니다.” 알림을 보낸다.

원칙:

- 요청 게시판에는 **반려(REJECTED), 재오픈(REOPEN), 검토중(IN_REVIEW)** 흐름을 두지 않는다.
- 요청은 작성 후 **취소 불가**로 처리한다. 따라서 요청 삭제/취소 API는 MVP에서 제공하지 않는다.
- 이미 `IN_PROGRESS`가 된 요청은 다른 TA가 다시 수락할 수 없다. 이미 assignee가 있으면 409 `REQUEST_ALREADY_ASSIGNED`.
- 요청 완료는 별도 `link-post` API 없이 `POST /api/posts`의 `linkedRequestId`로 자동 처리한다.
- 요청 상태 변경 알림은 DM으로 자동 발송한다. `REQUESTED → IN_PROGRESS` 때 요청자에게 수락/제작중 알림을 보내고, `IN_PROGRESS → COMPLETED` 때 요청자에게 제작 완료 알림을 보낸다.
- 어드민은 요청 흐름에 개입하지 않고 조회/모니터링만 한다.

### 에셋 공유 / 다운로드 승인 흐름

5/26 TA 전체 회의 이후 에셋 공유 정책은 다음처럼 변경한다.

- TA 사용자는 본인의 에셋을 `POST /api/posts`로 공유한다.
- 다른 사용자는 게시글과 파일 메타데이터는 볼 수 있지만, 실제 파일 다운로드는 바로 허용하지 않는다.
- 사용자가 파일을 다운로드하려고 하면 제작자에게 다운로드 요청이 생성된다.
- 제작자가 다운로드 요청을 승인하면, 요청자는 해당 파일을 다운로드할 수 있다.
- 다운로드 요청에는 MVP에서 반려 흐름을 두지 않는다. 상태는 `PENDING`, `APPROVED`만 사용한다.

```text
다운로드 요청 전송(PENDING) → 제작자 승인(APPROVED) → 다운로드 가능
```

권한 원칙:

- 파일 업로더/게시글 작성자는 본인 파일을 바로 다운로드할 수 있다.
- 다른 사용자는 승인된 다운로드 요청이 있어야 `GET /api/files/{fileId}`로 실제 파일을 받을 수 있다.
- 다운로드 요청이 `PENDING`이면 프론트는 “제작자 승인 대기 중”으로 표시한다.

## 1. 공통 응답 규칙

일반 JSON API는 모두 `ApiResponse` 래퍼를 사용한다.

```json
{
  "success": true,
  "data": {}
}
```

```json
{
  "success": false,
  "error": {
    "code": "ERROR_CODE",
    "message": "사용자에게 보여줄 수 있는 메시지"
  }
}
```

단, 파일 다운로드처럼 실제 바이너리를 반환하는 API는 `ApiResponse`로 감싸지 않는다.

모든 엔드포인트 표는 아래 컬럼 형식을 따른다.

```md
| Method | Path | 기능 | Auth | 요청 | 응답 | 상태 코드 | 비고 |
```

## 4. Request 게시판 · `/api/requests/`**

> 5/26 TA 전체 회의 반영: 요청 게시판은 **Unity/Unreal 반이 필요한 에셋을 요청하고, TA 반 사용자가 본인이 맡을 요청을 선택해서 수락하는 흐름**으로 단순화한다. 반려/재오픈/취소는 MVP에서 제외한다.

상태 흐름:

```text
REQUESTED(요청됨) → IN_PROGRESS(제작중 / TA 승낙) → COMPLETED(완료)
```

| Method | Path                        | 기능                   | Auth        | 요청                                      | 응답                                          | 상태 코드 | 비고                                            |
| ------ | --------------------------- | -------------------- | ----------- | --------------------------------------- | ------------------------------------------- | ----- | --------------------------------------------- |
| POST   | `/api/requests`             | 에셋 요청 작성             | ✅           | multipart `data`, `referenceThumbnail?` | `ApiResponse<RequestResponse>`              | 201   | status=`REQUESTED`. 작성 전 “취소 불가” 확인 팝업 필수 |
| GET    | `/api/requests`             | 요청 목록                | ✅           | `?page&size&status&assigneeId&requesterId&q` | `ApiResponse<PageResponse<RequestSummaryResponse>>` | 200   | 내부 회원만. TA가 맡을 요청 탐색                  |
| GET    | `/api/requests/{id}`        | 요청 상세                | ✅           | -                                       | `ApiResponse<RequestResponse>`              | 200   | `assigneeId`, `linkedPostId` 포함               |
| PUT    | `/api/requests/{id}`        | 요청 수정                | ✅(요청자)    | multipart `data`, `referenceThumbnail?` | `ApiResponse<RequestResponse>`              | 200   | `REQUESTED` 상태에서만 수정 가능. 취소는 불가       |
| PATCH  | `/api/requests/{id}/assign` | TA가 본인을 assignee로 수락 | ✅(USER/TA)  | - (본문 없음, 호출자 자동 assignee)       | `ApiResponse<RequestResponse>`              | 200   | 1명만 배정. 자동 `IN_PROGRESS` + 요청자에게 시스템 DM 발송. 이미 assignee 있으면 409 |

> **요청 취소 불가**: 요청자는 요청 작성 전 프론트 확인 팝업을 통해 “요청 등록 후 취소할 수 없음”을 안내받는다. 따라서 `DELETE /api/requests/{id}`는 MVP에서 제공하지 않는다.
>
> **반려/재오픈 없음**: `PATCH /api/requests/{id}/reject`, `PATCH /api/requests/{id}/reopen`은 제거한다.
>
> **자동 완료 흐름**: 별도 `/link-post` 엔드포인트는 두지 않는다. assignee가 에셋 게시글 작성 시 `POST /api/posts` 본문에 `linkedRequestId`를 넣으면 서비스가 요청 상태를 자동 `COMPLETED`로 전환하고 `linkedPostId`를 세팅한다.
>
> **어드민 개입 없음**: 본 흐름에는 `🛡` 권한 작업이 없다. 운영자는 `GET /api/requests`로 모니터링만 가능하다.

### 요청 상태 변경 DM 알림 규칙

요청 게시판 상태 변경은 `messages` 테이블을 사용해 시스템 DM으로 기록한다. 별도 알림 테이블은 MVP에서 만들지 않는다.

| 트리거 | 수신자 | 메시지 예시 | 처리 위치 |
| ------ | ------ | ----------- | -------- |
| `PATCH /api/requests/{id}/assign` 성공 | 요청자(requester) | `{assigneeNickname}님이 {requesterNickname}님의 요청을 수락해서 제작중입니다.` | RequestService |
| `POST /api/posts`에서 `linkedRequestId`로 완료 처리 | 요청자(requester) | `{assigneeNickname}님이 {requesterNickname}님의 요청 제작을 완료했습니다.` | PostService + RequestService |

구현 방식은 MVP에서는 **SYSTEM 사용자 계정**을 하나 두고 `messages.sender_id`로 사용한다. 이렇게 하면 현재 ERD의 `messages.sender_id NOT NULL` 구조를 유지할 수 있다. 추후 알림이 복잡해지면 `notifications` 테이블 또는 `messages.message_type` 컬럼을 v1.1에서 검토한다.

### 시스템 DM 알림

DM은 사용자 간 직접 메시지뿐 아니라 요청 게시판 상태 변경 알림에도 사용한다.

- TA가 요청을 수락하면 요청자에게 자동 DM을 보낸다.
- TA가 `linkedRequestId`로 결과 게시글을 작성해 요청이 완료되면 요청자에게 자동 DM을 보낸다.
- MVP에서는 별도 `notifications` 테이블을 만들지 않고 `messages` 테이블에 저장한다.
- 현재 ERD의 `messages.sender_id`가 `NOT NULL`이므로, 시스템 알림 발송용 `SYSTEM` 사용자 계정을 하나 둔다.
- 프론트는 일반 DM과 시스템 DM을 같은 수신함에서 보여주되, 시스템 메시지는 “시스템 알림” 스타일로 구분해 표시한다.

> **본 MVP 범위 외**: 어드민의 DM 강제 열람(`/api/admin/messages/`**)은 분쟁 처리가 우리 책임 영역이 아니므로 본 프로젝트에서 제외한다.
