| **요청 자동 완료** | assignee가 에셋 게시글 작성 시 `linkedRequestId` 박으면 트랜잭션 내에서 요청 `status → COMPLETED` 자동 전환 |
| **브랜치 / 환경** | `feature → dev → prod(테스트) → main(배포)` 3단. prod 프로파일은 MySQL + Docker compose |

> 아래 본문 다이어그램과 충돌 시 본 박스 우선.


> 비유: **아파트 한 동(모놀리스) 안에 8개 가구(도메인)가 사는 구조.** 각 가구는 자기 현관문(서비스 API)만 열어두고, 거실 가구 배치는 마음대로. 단, 공용 시설(전기, 수도 = 공통 설정)은 관리실(Infra)만 손댄다.

## 왜 "모듈러 모놀리스"인가 — 비유 + 이유

- **마이크로서비스(MSA) 풀세트**는 8명이 한 달 안에 다루기엔 과체중입니다. 게이트웨이, 서비스 디스커버리, 분산 트랜잭션, K8s ... 학습 효과보다 무거움이 더 큽니다.
- 대신 **모놀리스 한 통 안에 도메인 경계를 단단히** 그어둡니다. 비유하자면 **"한 건물 안에 여러 가게가 있되, 각 가게는 자기 출입문만 두는" 쇼핑몰**.
- 이렇게 두면 나중에 한 가게(ex. file)가 커지면 그 가게만 분리해 별도 서비스로 떼어내기 쉽습니다 (= 스트랭글러 패턴 준비).

### 도메인 간 통신 규칙 (한 줄)

> **"엔티티를 빌리지 말고, 서비스를 부르거나 ID만 들고 다닌다."**

| 좋은 패턴 | 나쁜 패턴 |
|---|---|
| `RequestService` 가 `MessageService.send(...)` 호출 | `RequestService` 가 `Message` 엔티티 직접 생성·저장 |
| `Post.authorId : Long` 으로 들고 다님 | `Post.author : User` 무겁게 fetch JOIN |
| 응답 DTO에 `{ "authorId": 7, "authorNickname": "kim" }` | 응답 DTO에 `User` 통째로 |

> 단, 이미 작성된 코드(`Post.author : User`)는 JPA의 `@ManyToOne(LAZY)` 로 안전. **새로 추가하는 도메인 간 연결**부터 이 규칙을 따릅니다.

## 인증 흐름 (JWT)

```
[클라이언트]                            [Spring Boot]
   │                                       │
   ├── POST /api/users/login ─────────────▶│  비번 검증 → JwtProvider.create()
   │                                       │
   │◀───────────── 200 { token, user } ────┤
   │                                       │
   │ Authorization: Bearer <jwt>           │
   ├── GET /api/posts ────────────────────▶│  JwtAuthenticationFilter
   │                                       │  → Authentication 등록
   │                                       │  → @PreAuthorize / RoleHierarchy 검사
   │◀───────────── 200 { posts } ──────────┤
```

- 토큰 만료: 기본 7일 (`jwt.expiration` 프로퍼티)
- WebSocket 인증: STOMP `CONNECT` 헤더의 `Authorization` 을 `StompJwtChannelInterceptor` 가 검사
- 익명 허용 엔드포인트: 회원가입/로그인, 카테고리 조회, h2-console, swagger

## 비기능 단면

### 트랜잭션

- 컨트롤러 → 서비스 → 리포지토리. 트랜잭션 경계는 **서비스 메서드** 에 둠 (`@Transactional`).
- 외부 도메인 서비스를 부를 때(예: RequestService → MessageService) **같은 트랜잭션** 안에 묶입니다. 그래서 send가 실패하면 상태 변경도 롤백.
- 비동기 작업은 v1.1 확장 지점으로 둡니다. MVP의 요청 상태 변경 DM은 같은 트랜잭션 안에 묶어 알림 누락을 막습니다.

### 캐시

- 인기 태그는 **Caffeine 인메모리 캐시** (`@Cacheable`, TTL 60s).
- v1.1에서 Redis 옮길 수 있도록 `CacheManager` 한 곳으로만.

### 로깅/관측

- 액세스 로그: Spring 기본 + 요청 ID(향후 MDC)
- 메트릭: `micrometer-registry-prometheus`, `/actuator/prometheus`
- 다운로드 로그/파일 통계는 MVP 범위 밖입니다. 필요하면 v1.1에서 Analytics/Audit 도메인으로 분리합니다.
