# 01. 용어집 (Glossary)

> 비유: **여행 회화책.** 외국 처음 가서 헷갈리는 단어를 그때그때 찾아보는 책.
> 기획 / 코드 / 협업 문서에 등장하는 모든 어려운 용어를 한 곳에서. 모르는 단어가 생기면 여기부터.

> 사용법: `Ctrl+F` 또는 `Cmd+F` 로 검색.

# 판교어 해독 예시 : 
판교어 : 

내일은 현재까지 발산된 기능 요구사항과 유저 시나리오를 MECE하게 decomposition한 뒤, MVP 관점에서 impact-effort matrix 기반 priority triage를 진행하겠습니다. 또한 지금까지 도출된 feature 후보군을 MVP scope 기준으로 filtering하고, 각 기능의 dependency chain과 potential blocking point를 선제적으로 식별한 뒤, API 명세서를 중심으로 팀 전체의 shared mental model을 align 하겠습니다.

특히 API 명세서는 앞으로 프론트엔드와 백엔드 사이의 contract layer이자 single source of truth로 기능해야 하기 때문에, 각 endpoint의 responsibility, request/response schema, exception handling policy를 명확히 맞추는 것이 핵심입니다.

이 과정을 통해 추후 sprint 진행 중 발생할 수 있는 communication overhead와 requirement ambiguity를 최소화하고, 각 팀원이 자신의 task ownership을 명확히 인지한 상태에서 implementation에 진입하는 것이 목표입니다.

결론적으로 내일의 목표는 단순한 기획 리뷰가 아니라, 요구사항을 execution-ready backlog로 전환하고, 월요일부터 바로 implementation phase에 진입 가능한 operational readiness를 확보하는 것입니다.

해석 : 내일 다 같이 기획 읽고, 기능 쪼개고, 우선순위 정하고, API 명세서 박아서 월요일부터 바로 개발 들어가자는 뜻

## A. 프로젝트 / 기획 용어

### MVP (Minimum Viable Product)
"최소한으로 작동하는 제품." 멋진 기능 없이도 한 사이클이 돌아가는 상태. 우리 M1 의 목표.
**비유**: 시제차에 에어컨·내비 없어도 바퀴 4개로 굴러가면 MVP.

### MoSCoW (모스코우)
우선순위 분류법. **MUST**(없으면 망함) / **SHOULD**(있어야 정상) / **COULD**(있으면 좋음) / **WON'T**(이번엔 안 함).

### 마일스톤 (Milestone)
큰 일정 단위. 우리는 M0~M3.
**비유**: 마라톤의 5km / 10km / 20km / 결승선 표지판.

### 스프린트 (Sprint)
짧은 작업 주기. 보통 1~2주. 본 프로젝트는 마일스톤 자체가 사실상 스프린트.

### 갠트 (Gantt) 차트
막대그래프로 보는 일정표. 한 줄이 한 작업, 가로 길이가 기간.

### EOD (End of Day)
"그날 퇴근 전까지." 6/16 EOD 면 6/16 자기 전.

### 데드라인 (Deadline)
넘기면 끝나는 마감일.

### 게이트 (Gate)
"통과 관문." 이 조건 못 채우면 다음 단계로 못 넘어감. 본 프로젝트는 마일스톤마다 게이트 있음.

### 게이트키퍼 (Gatekeeper)
"관문지기." 특정 영역(예: DDL 변경)에 들어오는 변경을 한 명이 검토해서 통과시키는 역할. 우리는 Infra가 DB 스키마 게이트키퍼.

### 트리아주 (Triage)
응급실 환자 분류처럼 이슈를 P0(지금 당장) / P1(이번 주) / P2(나중에) 로 나눠 우선순위 정하는 작업.

### 핫픽스 (Hotfix)
운영 중에 발견된 치명적 버그를 빨리 고쳐 긴급 배포하는 패치.

### 베타 (Beta)
정식 출시 전, 일부 사용자에게 먼저 공개해서 피드백 받는 단계. 우리는 6/9 TA반 베타 배포.

### 리허설 (Rehearsal)
본 공연(배포) 전에 똑같이 한번 해보는 예행연습.

### 회고 / KPT
프로젝트 끝나고 돌아보는 미팅. **Keep**(유지) / **Problem**(문제) / **Try**(시도) 세 칸으로 정리.

### 백로그 (Backlog)
"다음에 할 일 목록." 우선순위는 정해두되 지금은 안 함. 본 프로젝트는 v1.1 백로그.

### 인수 기준 (AC, Acceptance Criteria)
"이 기능이 완료됐다고 볼 조건들." 체크박스로 정리. 인수 기준 다 통과하면 그 기능 끝.

### PM (Project Manager)
프로젝트 매니저. 일정·역할·리스크를 관리. 본 프로젝트에선 시니어 기획자 역할도 겸함.

### 스탠드업 (Stand-up)
짧게 서서 진행하는 미팅이라는 데서 유래. 길어지지 말라는 의미. Slack 글로 대신해도 OK. 보통 매일 10분.

### 위클리 / 데일리
매주 / 매일 정기 미팅.

### 의식 (Ritual)
정기적으로 같은 시간에 같은 방식으로 하는 일 (스탠드업, 위클리, 회고 등).

## B. 아키텍처 / 시스템 용어

### 모놀리스 (Monolith)
모든 기능이 한 프로젝트 / 한 프로세스에 있는 구조. 한 통(monolith)이라는 뜻.
**비유**: 한 건물 안에 모든 가게가 입주.

### MSA (Microservice Architecture)
도메인마다 별개 서비스로 분리해 네트워크로 통신하는 구조.
**비유**: 시장처럼 가게마다 독립 건물.

### 모듈러 모놀리스 (Modular Monolith)
모놀리스인데 도메인 경계가 단단한 구조. **우리가 선택한 방식.** 같은 JVM이지만 패키지로 도메인을 나눔.
**비유**: 한 쇼핑몰 안에 가게들이 명확히 구분된 형태. 같은 지붕(공용 인프라)을 쓰되 가게 영역 침범 금지.

### 스트랭글러 패턴 (Strangler Fig Pattern)
처음엔 모놀리스로 시작하다가, 한 도메인이 커지면 그 부분만 떼어내 별도 서비스로 옮기는 점진적 전략. 우리도 v1.1 이후 file 도메인을 분리할 가능성을 열어둠.
**비유**: 큰 나무를 베지 않고, 줄기를 새 나무로 점점 감싸서 결국 교체.

### JVM (Java Virtual Machine)
자바 코드를 실행하는 가상머신. 우리 백엔드는 JVM 한 통에서 돌아감.

### 도메인 (Domain)
업무 영역. 우리는 User / File / Post / Request / Comment / Category / Tag / Message / Feedback 도메인.

### 컨트랙트 (Contract)
"약속." 다른 도메인이 나를 부를 때 어떤 메서드를 어떤 모양으로 부르는지 정한 인터페이스. 우리 기획 폴더의 04_api / 03_erd 가 컨트랙트.

### 컨트랙트 동결 (Contract Freeze)
"도면에 잉크 묻히기." 더 이상 안 바꾸는 시점. 우리는 5/26 EOD에 API/ERD 컨트랙트 동결.

### 단일 책임 원칙 (SRP, Single Responsibility Principle)
"하나의 클래스는 한 가지 일만." 객체지향 5대 원칙 중 하나.

### 모듈 (Module)
독립 단위. 본 프로젝트에선 도메인 패키지가 곧 모듈.

### 빈 (Bean)
Spring이 생성·관리하는 객체. `@Component`, `@Service`, `@Configuration` 등으로 등록.

### IoC / DI (Inversion of Control / Dependency Injection)
"필요한 객체를 직접 만들지 말고, 외부(Spring)가 주입하도록." 생성자 주입(`@RequiredArgsConstructor` + final 필드)이 권장 방식.

## C. Spring / Java 코드 용어

### 엔티티 (Entity)
JPA의 `@Entity` 클래스. DB 테이블 한 줄에 대응되는 자바 객체.

### Repository
DB와 대화하는 인터페이스. `JpaRepository<Post, Long>` 상속하면 `findById`, `save`, `findAll` 등 자동 제공.

### 서비스 (Service)
비즈니스 로직이 들어가는 계층. `@Service`. 트랜잭션 경계도 보통 여기.

### 컨트롤러 (Controller)
HTTP 요청을 받아 서비스로 넘기는 입구. `@RestController` + `@RequestMapping`.

### DTO (Data Transfer Object)
계층 사이 데이터 전달용 객체. 엔티티를 직접 응답으로 노출하지 않고 DTO로 매핑.

### JPA (Java Persistence API)
객체-관계 매핑(ORM) 표준. 우리는 Hibernate 구현체 사용.

### ORM (Object-Relational Mapping)
객체(Java)와 관계(DB 테이블) 사이 자동 매핑. SQL 직접 안 쓰고 메서드 호출로 처리.

### 트랜잭션 (Transaction)
"전부 성공 아니면 전부 롤백." DB 변경 묶음. `@Transactional`. 서비스 메서드에 둠.
**비유**: 송금. 출금만 되고 입금 실패하면 안 되니까 묶어서 한 번에 처리.

### 롤백 (Rollback)
트랜잭션 중간에 예외 나면 모든 변경 무효화.

### 커밋 (Commit) (DB)
트랜잭션 정상 종료 → DB에 변경 확정.

### 영속성 컨텍스트 (Persistence Context)
JPA가 트랜잭션 동안 엔티티를 관리하는 공간. 같은 트랜잭션 안에선 같은 엔티티가 한 인스턴스로 유지.

### Lazy 로딩 (지연 로딩)
연관 엔티티를 진짜 필요할 때만 가져옴. `@ManyToOne(fetch = LAZY)`. 기본 권장.

### Eager 로딩 (즉시 로딩)
연관 엔티티를 함께 가져옴. 잘못 쓰면 데이터 폭주.

### N+1 문제
목록 1번 쿼리 + 각 항목의 연관 N번 쿼리. 총 N+1 쿼리. 페이지 느려짐의 주범.
**해결**: fetch join, `@EntityGraph`, batch size.

### Fetch join
JPQL에서 연관까지 한 쿼리로 가져오는 기법. `select p from Post p join fetch p.author`. N+1 해결책.

### 낙관락 (Optimistic Lock)
"보통은 충돌 안 날 거야" 가정. `@Version` 컬럼 두고, 업데이트 시 버전이 맞으면 통과, 안 맞으면 예외. 좋아요 같은 가벼운 동시성에 적합.
**비유**: 도서관 책 빌려갈 때 "다른 사람도 동시에 못 빌려갈 거다"는 가정.

### 비관락 (Pessimistic Lock)
"무조건 충돌 난다" 가정해서 DB에 락. `SELECT FOR UPDATE`. 결제 같은 무거운 동시성.
**비유**: 책 자체를 손에 쥐고 안 놔주는 방식.

### Soft Delete
"플래그(`deleted=true`)만 세우고 실제 삭제 안 하기." 분쟁·복구 대응. 우리는 Post / Request / Comment 에 적용.

### Hard Delete
DB row + 디스크 파일 진짜 삭제. 본 MVP에서는 게시글/유저 어드민 강제 삭제에 사용하지 않는다.

### Bean Validation
`@NotBlank`, `@Size`, `@Email` 등의 어노테이션으로 입력값 검증. `@Valid` 와 함께 사용.

### `@Async`
"비동기로 돌려라." 메서드를 호출자와 다른 스레드에서 실행. 다운로드 로그 적재 같은 부차적 작업에 사용.
**주의**: 같은 빈 안에서 self-invocation 하면 적용 안 됨.

### `@Transactional`
트랜잭션 경계 선언. 메서드 시작 시 시작, 정상 종료 시 커밋, 예외 시 롤백.

### `@Cacheable` / Caffeine
"이 메서드 결과 캐싱해라." Caffeine 은 자바용 인메모리 캐시 라이브러리. 우리 인기 태그에 60초 TTL 적용.

### TTL (Time To Live)
"수명." 캐시가 살아 있는 시간. 60s 면 60초 후 만료.

### Lombok
보일러플레이트 코드(`getter`, `builder`, 생성자 등)를 어노테이션으로 자동 생성하는 라이브러리. `@Getter`, `@Builder`, `@RequiredArgsConstructor` 등.

## D. 인증 / 보안

### JWT (JSON Web Token)
로그인 후 받는 출입증 문자열. 위변조 못 하게 시그니처(서명)가 붙어 있음. 세 부분 (header.payload.signature) 으로 점(.) 으로 구분.
**비유**: 박물관 입장권. 검표원(서버)이 위조 여부 검사 가능.

### Bearer 토큰
`Authorization: Bearer <jwt>` 헤더 형식. "Bearer(소지자)"가 이 토큰을 들고 왔다는 의미.

### BCrypt
비밀번호 단방향 해시 알고리즘. 같은 비번이라도 매번 다른 해시 생성(salt). 우리는 가입·로그인 시 사용.

### CORS (Cross-Origin Resource Sharing)
프론트가 다른 도메인의 백엔드 API를 부를 수 있게 허용하는 규칙. 안 풀면 브라우저가 차단.
**비유**: 옆 동네 가게에 출입하려면 그 가게가 "당신 동네 손님 환영" 팻말을 걸어야 함.

### RoleHierarchy
권한 계층. 우리는 `SUPER_ADMIN > ADMIN > USER`. SUPER_ADMIN 은 자동으로 ADMIN 권한 포함.

### `@PreAuthorize`
메서드 호출 직전에 권한 검사. `@PreAuthorize("hasRole('ADMIN')")`.

### CSRF (Cross-Site Request Forgery)
다른 사이트에서 우리 사이트로 위장 요청 보내는 공격. JWT 사용 시 보통 CSRF 보호 disable.

### 세션 (Session)
서버가 사용자 상태를 메모리에 들고 있는 방식. 우리는 stateless JWT 라 세션 안 씀.

### Stateless
"상태 없음." 서버가 사용자 정보를 메모리에 안 들고 있고, 매 요청마다 토큰으로 누구인지 판단.

## E. HTTP / API

### REST (Representational State Transfer)
HTTP 메서드(GET / POST / PUT / DELETE)와 자원 URL 을 조합하는 API 설계 방식.

### HTTP 메서드
- **GET**: 조회 (몸값 없음, 멱등)
- **POST**: 생성·변경 (몸값 있음, 비멱등)
- **PUT**: 전체 교체 (멱등)
- **PATCH**: 부분 변경 (멱등)
- **DELETE**: 삭제 (멱등)

### 멱등 (Idempotent)
"여러 번 호출해도 결과가 같다." GET / PUT / DELETE 는 멱등, POST 는 비멱등.

### HTTP 상태 코드
- **2xx**: 성공 (200 OK, 201 Created, 204 No Content)
- **4xx**: 클라이언트 잘못 (400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 409 Conflict)
- **5xx**: 서버 잘못 (500 Internal Server Error)

### REST 폴링 (Polling)
"주기적으로 서버에 물어보기." 클라이언트가 5초마다 `/api/messages/unread` API를 호출해 새 게 있나 확인. 실시간은 아니지만 단순함. 우리 M1 DM 은 폴링.
**비유**: 1분마다 우편함 열어보기.

### Long polling
폴링의 변종. 서버가 새 데이터 있을 때까지 응답을 미룬 채 기다림. 우리는 안 씀.

### WebSocket
한 번 악수 후 양방향 상시 통신 유지. STOMP 는 그 위에 얹는 메시지 프로토콜.
**비유**: 인터폰. 한 번 누르면 끝날 때까지 연결.

### STOMP (Simple Text Oriented Messaging Protocol)
WebSocket 위에서 발행/구독(pub/sub) 패턴을 쉽게 쓰게 해주는 프로토콜. 우리는 Spring 의 `SimpMessagingTemplate` 사용.

### 구독 (Subscribe) / 발행 (Publish)
WebSocket pub/sub 패턴. 클라이언트는 토픽 구독 → 서버가 발행 → 구독자에게 푸시.

### Multipart / form-data
파일을 포함한 HTTP 요청 형식. 우리 게시글 작성 / 아바타 업로드에서 사용.

### Multipart Part 이름
multipart 요청 안의 각 조각 이름. 우리는 `data`(JSON), `files`(에셋), `thumbnail`(이미지).

### Content-Type
요청·응답 본문 형식. `application/json`, `multipart/form-data`, `image/png` 등.

### Content-Disposition
파일 다운로드 시 어떤 이름으로 저장할지 알려주는 헤더. `Content-Disposition: attachment; filename*=UTF-8''chair.fbx`.

### CORS preflight
브라우저가 본 요청 전에 `OPTIONS` 메서드로 "이거 보내도 돼?" 묻는 사전 요청.

### 페이지네이션 (Pagination)
큰 결과 목록을 페이지 단위로 잘라서 응답. `?page=0&size=20`.

## F. DB / 스키마

### DDL (Data Definition Language)
스키마 정의문. `CREATE TABLE`, `ALTER TABLE`. 우리는 dev 에서 `ddl-auto: create-drop` 으로 자동 생성, prod 에선 `validate`.

### DML (Data Manipulation Language)
데이터 변경문. `INSERT`, `UPDATE`, `DELETE`.

### 마이그레이션 (Migration)
DB 스키마 변경 이력 관리. Flyway / Liquibase 가 도구. 우리는 v1.1 도입.

### 인덱스 (Index)
DB의 책갈피. 조회 빠르게. `@Index(name = "idx_posts_author", columnList = "author_id")`. 너무 많으면 INSERT 느려짐.

### Primary Key (PK)
테이블의 고유 식별자. 우리는 `Long id` AUTO_INCREMENT.

### Foreign Key (FK)
다른 테이블의 PK를 참조하는 컬럼. JPA `@ManyToOne(...) @JoinColumn(name = "author_id")`.

### UNIQUE 제약
같은 값 두 번 못 들어가게 함. 이메일 UNIQUE.

### Cascade
부모 행 변경 시 자식도 따라 변경되도록. 잘못 쓰면 의도치 않은 대량 삭제.

### Soft delete (재등장)
플래그만 세움. 위 C 섹션 참고.

### H2
가벼운 자바 인메모리 DB. 개발에 사용. 웹 콘솔 `/h2-console`.

### MySQL
운영용 RDB.

### Redis
인메모리 키-값 저장소. 캐시·세션·메시지 큐. 우리는 v1.1.

### ERD (Entity-Relationship Diagram)
엔티티(테이블) 와 관계를 그린 다이어그램. 우리 03_erd 폴더.

## G. 파일 / 스토리지

### S3 (Amazon Simple Storage Service)
AWS 의 파일 스토리지 서비스. 우리는 v1.1 전환 검토. 본 MVP 는 로컬 디스크.

### Object Storage
파일을 "객체"로 다루는 스토리지. S3, GCS 등. 폴더 구조가 아닌 key-value.

### Presigned URL
"서명된 URL." 권한 검증을 해서 만든 일회용 URL. 인증 없이도 이 URL로 다운로드 허용. 우리 v1.1.

### Streaming
파일을 한 번에 메모리 올리지 않고 조각조각 전송. 대용량 파일에 필수.

### Multipart upload
큰 파일을 여러 조각으로 나눠 업로드. S3 의 5GB 이상 파일에 필요. 본 MVP 범위 아님.

## H. Git / 협업

### Git
분산 버전 관리 시스템.

### GitHub
Git 호스팅 서비스 + PR / 이슈 트래커.

### 브랜치 (Branch)
독립적인 작업 라인. `main`, `feat/post-create` 등.

### main 브랜치
배포 가능한 상태가 유지되는 메인 라인. 직접 push 금지.

### feature 브랜치
한 기능 단위 작업 브랜치. 짧게 살고 빨리 머지.

### fork — 본 프로젝트 사용 안 함
다른 사람/조직의 레포를 내 GitHub 계정으로 복사해서 별도 레포처럼 다루는 방식. 오픈소스 외부 기여자가 PR 보낼 때 쓰는 모델. **우리는 한 팀 레포에서 브랜치만 따서 작업**하므로 fork 사용 안 함.
**비유**: 남의 책 복사해서 내 책으로 들고 가서 작업.

### clone — 본 프로젝트 표준
원격 레포를 내 컴퓨터로 다운받기. `git clone <url>`. 팀 레포에 push 권한이 있는 사람의 기본 시작점.
**비유**: 팀 책꽂이의 책을 내 책상에 가져와 작업.

### clone
원격 레포를 내 컴퓨터로 가져오기.

### commit
변경 사항 하나의 묶음. 메시지 포함.

### push
내 커밋을 원격(GitHub)에 올리기.

### pull
원격의 새 커밋을 내 로컬로 가져오기.

### fetch
원격 변경 정보만 가져오고 병합은 안 함.

### merge
두 브랜치를 합침. 일반 merge / squash merge / rebase merge 세 종류. **본 프로젝트는 일반 merge (no-ff) 만 사용.**

### 일반 Merge (no-fast-forward) — 본 프로젝트 표준
PR 의 커밋을 그대로 살린 채 머지 커밋을 추가로 만든다. 누가 무엇을 했는지 추적 가능.
**비유**: 두 강이 만나서 합류 지점을 표시하고 같이 흐름.

### Squash merge — 본 프로젝트 사용 안 함
PR 의 여러 커밋을 한 커밋으로 압축해서 머지. 히스토리가 압축돼서 디버깅·되돌리기가 어려워짐.

### Rebase — 본 프로젝트 사용 안 함
내 브랜치의 base 를 main 의 최신 커밋으로 옮김. 히스토리는 직선적이지만, 충돌 해결이 모호해지고 협업 시 위험.
**비유**: 내 작업을 들고 다른 강 위로 옮겨 한 줄기로 만듦. 우리는 합류 지점을 보존하는 방식이 더 안전하다고 판단.

### Force push — 본 프로젝트 사용 안 함
원격 브랜치를 강제 덮어쓰기. 위험. 일반 merge 정책이라 사용할 일도 없음.

### Pull Request (PR)
"내 브랜치를 main 에 합쳐주세요" 요청. 코드 리뷰 단위.

### 리뷰어 (Reviewer)
PR을 검토하는 사람. 우리는 작성자가 [`08_collaboration/01_Git_브랜치_PR_규칙.md`](../08_collaboration/01_Git_브랜치_PR_규칙.md) 의 표를 보고 **수동 지정**한다.

### CI (Continuous Integration)
PR 열리면 자동으로 빌드·테스트 돌리는 자동화. 우리는 GitHub Actions.

### CD (Continuous Deployment)
빌드 통과 시 자동 배포. 본 프로젝트는 수동 배포 (학습 효과).

### CI 그린 / 레드
CI 통과(초록 체크) / 실패(빨간 X).

### 머지 충돌 (Merge Conflict)
같은 줄을 두 사람이 다르게 고쳐 Git이 자동 병합 못 함.

### `.gitignore`
Git이 추적 안 할 파일 패턴. `build/`, `*.class`, `data/`, `uploads/` 등.

### CHANGELOG
변경 이력 정리 파일.

### RACI
역할 분담 표기법. **R**esponsible(실행) / **A**ccountable(최종 책임) / **C**onsulted(상의) / **I**nformed(통보).

## I. 테스트 / 품질

### 단위 테스트 (Unit Test)
한 메서드 / 한 클래스를 좁게 테스트. 의존은 Mockito 로 가짜화.

### 통합 테스트 (Integration Test)
여러 컴포넌트를 실제로 연결해 한 시나리오를 끝까지 돌려봄. "회원가입 → 게시글 작성 → 다운로드" 같은 사용자 흐름.

### 회귀 테스트 (Regression Test)
"예전에 잘 되던 게 새 코드로 망가지지 않았나" 다시 확인. 목적은 퇴보(regression) 막기.

### Smoke test
"불 붙여보고 연기 나나" 정도의 기본 동작 확인. 가장 가벼운 테스트.

### E2E (End-to-End)
프론트부터 백엔드까지 진짜 사용자 시나리오로 테스트. 가장 비싸지만 가장 신뢰.

### `@WebMvcTest` / `@DataJpaTest`
Spring 의 슬라이스 테스트. 일부 계층만 띄움.

### `@SpringBootTest`
전체 컨텍스트를 띄우는 통합 테스트.

### TestContainers
테스트용으로 Docker 컨테이너(MySQL 등) 임시 띄우는 라이브러리. v1.1.

### Mockito
가짜 객체(mock) 만드는 라이브러리. 단위 테스트에서 의존 격리.

### Coverage (커버리지)
테스트가 실제 코드의 몇 % 를 거치는지. Jacoco 가 도구.

## J. 운영 / 모니터링

### Docker
컨테이너 가상화. "내 컴퓨터에선 되는데" 문제 해결.

### Docker Compose
여러 컨테이너를 한 번에 띄우는 도구. `docker compose up` 한 줄.

### Container
앱과 그 환경을 묶은 격리된 실행 단위.

### Image
컨테이너의 정지 상태. 빌드되면 이미지, 실행되면 컨테이너.

### Kubernetes (K8s)
컨테이너 오케스트레이션. 본 프로젝트는 안 씀.

### Prometheus
백엔드 메트릭(요청 수, 응답시간, JVM 메모리 등) 주기적으로 긁어 저장하는 모니터링.

### Grafana
Prometheus 등의 데이터를 시각화하는 대시보드. v1.1 또는 학습 옵션.

### `/actuator/health`
Spring Boot 의 헬스체크 엔드포인트. "살아 있어?" 확인.

### `/actuator/prometheus`
Spring Boot 가 노출하는 Prometheus 형식 메트릭.

### 헬스체크 (Health Check)
"앱이 살아 있나" 확인용 가벼운 엔드포인트. 운영자 / 로드밸런서가 주기적으로 호출.

### 메트릭 (Metric)
숫자 측정값. 응답시간 / 요청 수 / 에러율 등.

### 로깅 (Logging)
이벤트를 글로 기록. `log.info(...)`.

### MDC (Mapped Diagnostic Context)
요청별 로그에 동일 컨텍스트(예: requestId) 자동 첨부.

### 옵저버빌리티 (Observability)
"시스템 안에서 무슨 일이 일어나는지 외부에서 알 수 있는 정도." 메트릭 / 로그 / 트레이스 3가지가 기둥.

## K. 도메인 특화 용어 (AssetBox)

### 에셋 (Asset)
3D 모델 파일 묶음. fbx / blend / obj / glb / gltf / zip + 썸네일.

### 포스트 (Post)
일반 게시글. 에셋을 공개.

### 리퀘스트 (Request)
요청 게시판 게시글. "이런 에셋이 필요해요" 의뢰. 상태 5단계.

### 상태 전이 (State Transition)
상태가 다른 상태로 바뀌는 것. Request: REQUESTED → IN_REVIEW → IN_PROGRESS → COMPLETED.

### State Machine
허용되는 상태 전이 규칙의 집합. 표 외 전이는 거부.

### 배정 (Assign)
요청에 TA를 지정하는 것. `PATCH /api/requests/{id}/assign`.

### 카테고리 트리
대(1) / 중(2) / 소(3) 3단계 셀프 참조 트리.

### Lazy 드릴다운
한 번에 트리 전체 안 가져오고, 클릭마다 자식만 가져오는 방식.

### 태그 (Tag)
자유 입력 키워드. 카테고리 보완재. findOrCreate 패턴.

### findOrCreate
"있으면 가져오고 없으면 만든다" 패턴. Tag 처리에 사용.

### teamId 스냅샷
게시글 작성 시점의 작성자 팀ID를 게시글에도 박아두는 패턴. 팀 이동 후에도 과거 글의 소속 추적.

### DM (Direct Message)
1:1 메시지. 우리 `message` 도메인.

### 시스템 발신자
요청 상태 변경 알림 등을 보내는 가상 유저. AdminBootstrapRunner 가 부팅 시 보장.

### 인박스 (Inbox)
대화 상대별 최신 메시지 요약 목록.

### 대화 (Conversation)
두 유저 간 메시지 모음. 시간 순 정렬.

### Unread
안 읽은 메시지. 헤더 뱃지에 표시.

## L. 자주 등장하지만 한 줄로

| 용어 | 한 줄 |
|---|---|
| API | 서비스 간 약속된 호출 인터페이스 |
| Endpoint | 한 API의 URL + 메서드 조합 |
| Endpoint URL | `GET /api/posts` 같은 한 줄 |
| URL | 인터넷 주소 |
| URI | URL 의 더 일반적인 이름 |
| JSON | 키-값 데이터 표현 형식 |
| Payload | 요청·응답의 본문 데이터 |
| Header | 요청·응답의 메타 정보 |
| Body | 요청·응답의 본문 |
| Status / 상태 코드 | 200, 404 같은 응답 분류 숫자 |
| Async | 비동기. 호출자가 안 기다림 |
| Sync | 동기. 호출자가 기다림 |
| Race condition | 동시 접근으로 결과가 꼬이는 현상 |
| Deadlock | 두 작업이 서로의 락을 기다리며 멈춤 |
| OOP | 객체지향 프로그래밍 |
| Dependency | 의존성. 내가 쓰는 라이브러리 / 클래스 |
| Library | 호출해서 쓰는 코드 묶음 |
| Framework | 우리 코드를 끼워 넣는 큰 틀 (Spring) |
| Compile | 자바 소스 → 바이트코드 |
| Build | 컴파일 + 패키징 |
| Deploy | 배포 |
| Runtime | 실행 중 시점 |
| Logger | 로그 출력기 |
| Exception | 예외. 처리 안 하면 죽음 |
| Stack trace | 예외 발생 시 호출 경로 |
| MVC | Model-View-Controller. Spring 의 기본 패턴 |
