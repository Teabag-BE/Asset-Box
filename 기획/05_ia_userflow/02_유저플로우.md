# 02. 유저 플로우 (역할별 핵심 시나리오)

> ⚠️ **2026-05-22 회의 반영** — 본 문서는 회의 결과를 반영한 패치본. 회의록 단일 진실 원본은 [`04_api/02_엔드포인트_목록_상태코드분리_수정본.md`](../04_api/02_엔드포인트_목록_상태코드분리_수정본.md).

## 회의 반영 유저플로우 변경 (핵심 — 본 박스가 최신)

### 새 흐름 1: OAuth 로그인 (Google)

```
[게스트] "Google 로 시작" 클릭
   → /api/oauth2/authorization/google
   → Google 인증
   → 콜백 → 이메일 화이트리스트 검사
       ├─ 통과 → JWT 발급
       └─ 미통과 → 403 OAUTH_EMAIL_NOT_WHITELISTED
   → 첫 가입이면 major 입력 페이지로 강제 리다이렉트
   → major 입력 후 자유 사용
```

### 새 흐름 2: 요청 자동 완료 (어드민 개입 없음)

```
[Unity/Unreal 반] 요청 작성 (REQUESTED)
   ↓
[TA] 요청 목록에서 발견 → /assign (본인을 assignee) → IN_PROGRESS
   ↓ (시스템 DM: "박TA가 수락했습니다")
[TA] 작업 → 에셋 게시글 작성 시 linkedRequestId 박음
   ↓
서비스가 자동으로 요청 status → COMPLETED, linkedPostId 세팅
   ↓ (시스템 DM: "요청이 완료되었습니다 → /posts/{id}")
[요청자] DM 클릭 → 결과 게시글로 이동
```

> GitHub Issue 가 PR 머지로 자동 닫히는 패턴과 동일. **별도 `link-post` 버튼 없음.**

### 제거된 흐름

- 비회원 익명 다운로드 — 회원만 가능
- 어드민 분쟁 조사 (메시지 강제 열람, 게시글 강제 삭제) — 본 MVP 범위 외
- Request `/review` 어드민 검토 단계 — 본 MVP는 REQUESTED → IN_PROGRESS 직행

> 아래 본문의 옛 플로우와 충돌 시 본 박스 우선.


> 비유: **놀이공원 동선표.** 어떤 게이트로 들어와서, 어떤 어트랙션을 거치고, 어디로 나가는지.
>
> 백엔드 입장에서 이 동선표가 중요한 이유: **한 동선에 등장하는 API들이 끊김 없이 협력해야 한다.** 동선 한 칸이 깨지면 사용자가 막힌다.

## 플로우 1. 게스트 → 회원 → 첫 열람/다운로드

```
[게스트]
   │
   ▼
랜딩(/) → 로그인/회원가입 선택
   │
   ▼ /signup
   ─── POST /api/users/signup ─── 201
   │
   ▼ /login
   ─── POST /api/users/login ─── 200 { accessToken, tokenType, profileRequired }
   │
   ├─ profileRequired=true → /profile/complete
   │      └─ PUT /api/users/me ─── major 최초 보완 (이미 설정된 major 재수정은 불가)
   │
   ▼ /posts
   ─── GET /api/posts (정렬: 최신)
   │
   ▼ 게시글 목록 클릭 → 상세
   ─── GET /api/posts/{id}
   ─── GET /api/files/{fileId}  ← 로그인 사용자만 다운로드/이미지 조회
   │
   ▼ 좋아요
   ─── POST /api/posts/{id}/like ─── { liked: true, likeCount: ↑ }
```

**핵심 컨트랙트**: 일반 에셋/파일은 비회원 열람 불가. 로그인 후에도 직전 URL로 복귀. 프론트가 redirect 처리.
**도메인 협업**: User(인증) → Post(상세) → File(다운로드) → Post(좋아요).

## 플로우 2. TA → 에셋 게시글 업로드

```
[USER (TA)]
   │
   ▼
로그인 → /posts/new
   │
   ▼ 폼 작성: 제목/본문/카테고리 선택(트리 드릴다운)
   ─── GET /api/categories/roots          (대분류, 로그인 필요)
   ─── GET /api/categories/{id}/children  (중·소분류 단계별, 로그인 필요)
   │
   ▼ 태그 입력 (free input)
   │
   ▼ 파일 선택: 모델파일 + 썸네일
   │
   ▼ 제출
   ─── POST /api/posts (multipart)
         ├─ Post 저장 (teamId 스냅샷)
         ├─ Tag findOrCreate (TagService)
         ├─ FileService.save(purpose=ASSET) × N
         ├─ 썸네일 저장 후 Post.thumbnailFileId 세팅
         ├─ linkedRequestId 있으면 Request 자동 COMPLETED
         └─ 응답: PostResponse{id, files[], tags[]}
   │
   ▼
/posts/{id} 로 이동 → 본인 게시글 확인
```

**핵심 컨트랙트**: 한 번의 multipart 요청으로 끝남. 부분 실패 시 트랜잭션 롤백.
**도메인 협업**: Post → File-A(저장) → Tag(findOrCreate) → Category(검증).

## 플로우 3. 요청 사이클 (요청 → 배정 → 작업 → 완료)

```
[USER 김씨 (요청자)]                                      [USER 박씨 (TA)]
   │                                                          │
   ▼ /requests/new                                            │
   ─── POST /api/requests (multipart data, referenceThumbnail?)│
       status=REQUESTED                                       │
   │                                                          │
   │                                                          ▼ /requests
   │                                                          ─── GET /api/requests
   │                                                          ─── PATCH /api/requests/{id}/assign
   │                                                              (본문 없음, 호출자=assignee)
   │                                                              status=IN_PROGRESS
   │◀── 시스템 DM "박씨가 요청을 수락했습니다" ───────────────────┤
   │                                                          │
   │                                                          ▼ 작업 + 게시글 업로드
   │                                                          ─── POST /api/posts
   │                                                              data.linkedRequestId = 요청 id
   │                                                              status=COMPLETED, linkedPostId=새 글 id
   │◀── 시스템 DM "요청 완료 → /posts/{id}" ─────────────────────┤
   │
   ▼ DM에서 링크 클릭 → 결과 다운로드
   ─── GET /api/files/{fileId}
```

**핵심 컨트랙트**: 상태 변경 시 **항상** `MessageService.send(...)` 호출. 깜빡하면 김씨가 결과를 못 본다.
**도메인 협업**: Request → User(assignee=현재 사용자 검증) → Post(`linkedRequestId` 자동 완료) → Message(알림).

## 플로우 4. 댓글 → DM 전환

```
[USER A]                             [USER B]
   │                                    │
   ▼ /posts/{id}                        │
   ─── GET .../comments ─ 본다          │
   ─── POST .../comments {parentId=null}│
   │                                    ▼ 알림 X (M1 범위는 아님)
   │                                    /posts/{id}
   │                                    ─── POST .../comments {parentId=A의 댓글id}
   │
   ▼ B의 답글 본문 안 "DM으로 이야기하시죠" 링크 클릭
   ─── 라우트: /messages/{B.id}
   ─── GET /api/messages/conversation/{B.id}
   ─── POST /api/messages {toUserId: B.id, content: "..."}
        └─ WS 푸시: B의 /user/queue/messages
```

## 플로우 5. ADMIN — 모니터링 + 피드백 확인

```
[ADMIN]
   │
   ▼ /admin/feedback
   ─── GET /api/admin/feedback ─ 신규 피드백 본다
   │
   ▼ /admin/posts ─ 게시글 현황 조회
   ─── GET /api/admin/posts?authorId=X
   │
   ▼ /admin/users ─ 유저 현황 조회
   ─── GET /api/admin/users?role=USER&q=...
   │
   ▼ 필요시 SUPER_ADMIN이 권한 변경
   ─── PATCH /api/admin/users/X/role {role: ADMIN}
   │
   ▼ 피드백 읽음 처리
   ─── PATCH /api/admin/feedback/{id}/read
```

**범위 밖**: 게시글 강제 삭제, 유저 강제 삭제/제재, DM 강제 열람, 분쟁 조사 API.

## 플로우 6. 검색

```
[USER 누구나]
   │
   ▼ 글로벌 헤더 검색바: "wooden chair"
   ─── GET /api/posts?q=wooden+chair&sort=likeCount,desc
   │
   ▼ 결과 + 좌측 사이드바에 인기 태그
   ─── GET /api/posts/popular-tags?limit=10
   │
   ▼ 태그 "furniture" 클릭
   ─── GET /api/posts?tag=furniture
   │
   ▼ 카테고리 필터 추가 (사이드바)
   ─── GET /api/posts?tag=furniture&categoryId=12
```

**핵심 컨트랙트**: 모든 검색은 `GET /api/posts` 한 입구. 정렬·필터는 쿼리 파라미터 결합.
**도메인 협업**: Post(검색 쿼리) + Tag(이름→ID 변환) + Category(검증).

## 플로우 7. 운영 모니터링 (운영자가 보는 시점)

```
[ADMIN]
   │
   ▼ /admin/stats
   ─── GET /actuator/prometheus  (운영 정책/IP/토큰 게이트)
   │
   ▼ /admin/feedback
   ─── GET /api/admin/feedback?status=NEW

   ─── GET /api/admin/posts
   ─── GET /api/admin/users
```

Infra는 동시에 `/actuator/prometheus` 를 통해 시스템 메트릭 확인.

## 플로우들에서 자주 등장하는 도메인 협업 매트릭스

> "내가 만든 도메인을 누가 호출할까?"의 답.

| 호출하는 쪽 | 호출당하는 쪽 | 시점 | 어떻게 |
|---|---|---|---|
| Post | File | 게시글 작성 / 수정 | `FileService.save/saveAll(...)` |
| Post | Tag | 게시글 작성 / 수정 | `TagService.findOrCreate(...)` |
| Post | Category | 게시글 작성 / 수정 | `CategoryService.requireExists(...)` |
| Post | File | 다운로드/이미지 조회 | `FileService.load(fileId)` |
| Post | Request | `linkedRequestId` 자동 완료 | `RequestService.completeByLinkedPost(...)` |
| Request | Message | 상태 전이 | `MessageService.send(systemSender, requester, ...)` |
| Request | User | assign | 현재 로그인 유저를 assignee로 사용 |
| Comment | Post / Request | 댓글 작성 | `PostService` / `RequestPostService.requireExists` |
| Message | User | 메시지 송신 | `UserService.requireExists(toUserId)` |

이 매트릭스는 `07_part_guides/` 의 각 파트별 가이드에 다시 나옵니다.
