# 04. Weekly Red Team Review (도메인 방어)

> 비유: **사내 모의 해킹.** 본인 도메인을 "공격당하는 입장"에서 방어해보면, 실제 운영에서 깨질 곳을 미리 본다.
>
> 매주 1회 각 담당자가 자기 도메인을 10분간 리뷰하고, 다른 팀원이 공격자(red team) 관점으로 질문해 약점을 찾는 자리.

> 모르는 단어는 [`../00_overview/01_용어집.md`](../00_overview/01_용어집.md) 참고.

---

## 1. 목적

- 도메인별 책임 범위를 팀 전체가 같이 공유
- API / 데이터 흐름 / 예외 처리 검증
- 기능 간 의존성(dependency) 및 막힌 지점(blocking point) 식별
- 구현 전/후 리스크 조기 발견
- **팀 전체가 같은 그림을 보고 있는지 정렬** (shared mental model)

> **shared mental model** = "다 같이 같은 그림을 머리에 그리고 있는 상태." 한 명이 따로 다른 그림을 그리면 통합 시점에 깨짐.

---

## 2. 시점

- **매주 금요일 1시간** (코드 리뷰 데이와 통합)
- 한 회차에 2~3명씩 발표. 한 달이면 모든 도메인 담당자가 1~2회 발표.

> 일정 상세는 [`../01_planning/01_마일스톤_일정.md`](../01_planning/01_마일스톤_일정.md) 의 "데일리·위클리 의식" 표 참고.

---

## 3. 진행 방식 (한 사람당 10분)

각 담당자는 다음 항목을 순서대로 설명한다.

1. 담당 도메인의 책임
2. 주요 기능과 프로세스
3. 핵심 코드 흐름
4. API 요청 / 응답 구조
5. 현재 막힌 지점(blocking point)
6. 다음 작업 계획

발표 후 팀원들이 **red team 관점**으로 질문한다.

**공격 질문 템플릿**:

- "이 기능은 **왜 필요한가?**" — 진짜 필요한 거 맞나?
- "이 API는 **프론트에서 사용하기 쉬운가?**" — 호출자가 헷갈리는 부분 없나?
- "**예외 상황**은 처리되어 있는가?" — 잘못된 입력, 권한 부족, 동시성 이슈
- "**권한 문제**는 없는가?" — 누가 무엇을 할 수 있는지 명확한가?
- "**데이터 정합성**이 깨질 가능성은 없는가?" — 트랜잭션, 부분 실패
- "다른 도메인과의 **의존성**은 명확한가?" — 강결합 / 순환참조 위험

리뷰에서 발견된 문제는 **GitHub Issue로 등록**하고, 이후 PR을 통해 수정한다.

---

## 4. 설명자의 역할

설명자는 **단순 발표가 아니라 자기 도메인에 대한 깊이 검증을 받는 자리**임을 인지한다.
질문에 답하면서 자신의 설계 의도를 방어하고, 동시에 논리적 취약점·개선점을 발견한다.

설명자는 다음 항목을 **명확히 설명할 수 있어야 한다**:

- 이 도메인이 **어떤 책임**을 가지는가
- **왜 이런 구조**로 설계했는가
- 어떤 **대안**이 있었고 왜 선택하지 않았는가
- 현재 구현의 **취약점**은 무엇인가
- **개선 가능한 지점**은 무엇인가
- 다른 도메인과 **어떤 의존성**을 가지는가
- **예외 상황과 edge case** 는 어떻게 처리되는가
- API 요청/응답 구조는 **왜 이렇게** 설계되었는가

답하지 못하는 질문은 모두 GitHub Issue 로 남기고 다음 주에 답한다. 모르는 걸 인정하는 게 정답.

---

## 5. PR 과 Red Team Review의 차이

비유로:

- **PR** = "**이 코드** 합쳐도 돼?" (코드 변경분에 대한 머지 검증)
- **Red Team Review** = "**우리 설계** 이대로 가도 돼?" (도메인 / 설계 / 리스크에 대한 팀 단위 검증)

| 구분         | PR                                | Red Team Review                                |
| ---------- | --------------------------------- | ---------------------------------------------- |
| 목적         | 코드를 공용 브랜치(dev)에 머지하기 전 검증        | 도메인·설계·API·리스크를 팀 단위로 검증                       |
| 시점         | 기능 구현 후, 머지 전                     | 매주 금요일 정기                                      |
| 단위         | 특정 feature 브랜치의 코드 변경분            | 각 도메인의 전체 책임과 흐름                               |
| 장소         | GitHub Pull Request               | 화상 / 오프라인 미팅                                   |
| 중심 질문      | "이 코드를 머지해도 되는가?"                 | "이 설계가 실제 구현/협업에서 버틸 수 있는가?"                   |
| 결과물        | 리뷰 코멘트, 승인, 머지                    | GitHub Issue, 액션 아이템, API 수정 제안, 설계 보완         |
| 자동 검사      | CI (테스트, 빌드 검사)                   | 사람 중심 토론                                       |
| 연결 방식      | PR 통과 → dev/main 머지                | 발견된 문제 → Issue 생성 → feature 브랜치 → PR → 머지       |

---

## 6. 흐름 — 발견에서 해결까지

```
Weekly Red Team Review
        ↓
리스크 / 문제 발견
        ↓
GitHub Issue 생성  ← 라벨: red-team, 우선순위(P0/P1/P2)
        ↓
feature 브랜치 (이름 끝에 #이슈번호 붙임)
        ↓
PR 생성
        ↓
코드리뷰 + CI 검사
        ↓
dev에 merge
```

**예시**:

> Red Team Review 에서: *"게시글 삭제 시 첨부된 3D 모델 파일 처리가 불명확하다."*

→ Issue 생성:
```
[Post/File] 게시글 삭제 시 첨부파일 상태 처리 정책 정의
label: red-team, P1
```

→ 담당자가 브랜치:
```
feature/post-file-delete-policy/#42
```

→ 수정 후 PR → dev 머지.

---

## 7. 운영 팁

- **발표자 사전 준비**: 자기 도메인의 `07_part_guides/<본인>.md` 와 `04_api/<본인 명세>.md` 를 다시 한 번 정독.
- **시간 엄수**: 1인 10분 설명 + 5~10분 Q&A. 길어지면 별도 미팅으로.
- **공격은 사람이 아니라 설계에 대해서.** "이 부분은 위험해 보임"이 OK, "왜 이렇게 만들었어?"는 NG.
- **모른다고 답하는 게 정답.** 약점을 숨기지 말 것. 숨긴 약점이 통합 시점에 폭발.
- **회의록 작성**: PM 이 발견된 이슈 리스트만 정리해 `01_planning/회의록/red-team-YYYY-MM-DD.md` 로 저장.

---

## 8. 첫 회차 권장 (M0~M1 시점)

M0 마지막 주(5/26 전후) 첫 Red Team Review:

- 발표자: 가장 의존성이 많은 도메인 먼저 — **User / File / Post** (3명)
- 다른 도메인은 다음 주(M1 중) 발표

이렇게 두면 모든 도메인의 핵심 컨트랙트가 일찍 검증된다.
