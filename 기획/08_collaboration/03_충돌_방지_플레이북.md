# 03. 머지 충돌 방지 플레이북

> 비유: **8개 차선이 만나는 회전교차로.** 신호등(컨트랙트)과 진입 우선순위 룰만 잘 지키면 절대 안 부딪힌다. 안 지키면 매번 사고.

> 본 문서는 "팀원들이 합칠 때 에러 많이 발생할까봐 걱정"이라는 우려를 정조준한 운영 매뉴얼.

---

## 충돌이 잘 나는 7가지 상황 + 처방

### 1) 같은 `SecurityConfig` 를 둘 이상이 수정

**왜 위험**: 새 엔드포인트의 permitAll 추가, ROLE 매핑이 한 파일에 몰림.

**처방**:

- 변경 시 슬랙 `#assetbox-arch` 채널에 "지금부터 SecurityConfig 수정합니다" 선언
- 변경은 항상 하루 안에 머지. 묵히면 다른 사람이 못 건드림
- 리뷰어로 User + Infra 수동 지정 (PM 이 스탠드업에서 누락 점검)

### 2) 새 엔티티 / 컬럼 동시 추가

**왜 위험**: ddl-auto 가 매번 재생성하지만, prod에선 충돌. dev에서도 시드/관계가 어긋남.

**처방**:

- 엔티티/컬럼 변경은 항상 별도 작은 PR
- PR 제목에 `[ERD]` 태그 + `03_erd/01_ERD.md` 동시 수정
- Infra가 게이트키퍼 — 작성자가 Infra 를 리뷰어로 수동 추가

### 3) 같은 패키지의 `Repository` 에 메서드 추가

**왜 위험**: 한 파일에 여러 명이 N개 메서드 추가하면 import 줄에서 충돌.

**처방**:

- 리포지토리에 메서드 추가는 도메인 오너 한 명만. 다른 도메인이 필요하면 **서비스에 메서드 추가 요청**으로 우회.
- 한 PR에서 한 메서드만 추가 (작게 머지)

### 4) WebSocketConfig / AsyncConfig 동시 수정

**왜 위험**: 빈 등록 충돌, 토픽 prefix 변경이 DM 전체에 영향.

**처방**:

- DM 담당과 Infra가 페어 PR
- WebSocketConfig 변경은 매주 월요일 위클리 안건으로만

### 5) `application.yml` 에 환경변수 새로 추가

**왜 위험**: 운영 환경에서 변수 누락 → 침묵 실패.

**처방**:

- `application.yml` 에 `${VAR:default}` 형태로 추가
- `.env.example` 도 같이 수정
- Infra 리뷰 필수

### 6) 응답 DTO에 필드 추가 / 제거

**왜 위험**: 프론트가 깨짐. 다른 도메인이 그 DTO를 사용하면 더 큼.

**처방**:

- 응답 DTO는 추가는 자유, **제거 / 이름 변경은 위클리 안건**
- 변경 시 `04_api/02_엔드포인트_목록.md` 동시 수정
- 프론트 담당과 슬랙 통보

### 7) Tag / Category / Comment 정책 변경

**왜 위험**: Post-A와 Post-B 양쪽이 다 호출하기 때문.

**처방**:

- 본 파트(Comment+Cat+Search) 가 정책 오너. 변경 시 Post-A + Post-B 리뷰어 추가

## 매주 충돌 예방 절차

### 월요일 (위클리 회의 안건)

1. 이번 주 머지 예정 PR 중 **공유 자원 변경** 있는 것 미리 공유
2. **컨트랙트 변경** (ERD / API) 있는 것은 회의에서 결정 → 별도 PR 즉시 머지
3. 도메인 간 협업 일정 조정

### 매일 (스탠드업)

- 어제 변경한 파일이 공유 자원이면 명시
- 오늘 손댈 파일이 공유 자원이면 미리 통보

### 통합 테스트 데이 (5/30, 6/6)

1. 모두 main 최신화
2. 도메인별 데모 5분씩
3. 사이클 한 번 돌리기 (8명 다 같은 자리)
4. 깨지는 부분 즉시 이슈 등록

## 리뷰어 수동 지정 (CODEOWNERS 사용 안 함)

PR 작성자가 [`01_Git_브랜치_PR_규칙.md`](./01_Git_브랜치_PR_규칙.md) 의 리뷰어 지정 표를 보고 **수동으로 추가**합니다. CODEOWNERS 자동 지정은 사용하지 않습니다.

- 공유 자원(SecurityConfig 등) 변경 → User + Infra + PM 수동 추가
- 도메인 코드 변경 → 페어(있다면) + PM 수동 추가
- PM 이 매일 스탠드업에서 리뷰어 누락 PR 점검

## "충돌 났을 때" 표준 절차

1. **혼자 30분 이상 끙끙대지 않는다.** 슬랙 `#assetbox-help` 에 즉시 핑.
2. **dev 최신화 시도**: `git fetch origin && git merge origin/dev` (rebase 사용 금지)
3. **충돌 파일 분류**:
  - 본인 도메인 파일 → 본인이 해결
  - 공유 자원 (SecurityConfig 등) → 변경자 + 본인이 화상 페어
4. **해결 후 일반 push** (force push 사용 금지 — 머지 커밋이 그대로 남아 안전)
5. **CI 재확인 후 머지**

---

## "이 PR은 좀 위험한데?" 체크리스트 (PM/리뷰어용)

PR을 받으면 5초 안에 체크:

- 변경 파일 중 `common/` 이 있는가? → 공유 자원, 신중
- 엔티티 (`domain/*.java`) 변경이 있는가? → Infra 리뷰
- API 변경 (`@*Mapping`) 이 있는가? → `04_api/` 동시 수정 확인
- PR 크기가 400 LoC 넘는가? → 쪼개기 요청
- 1주일 이상 묵은 브랜치인가? → 시급 머지 또는 새로 시작

---

## "비상 시" — 6/9 배포 직전에 핫픽스가 필요할 때

1. main 에서 `hotfix/<주제>` 브랜치 분기
2. 변경 최소화 (한 함수, 한 줄도 가능)
3. PM + 영향 도메인 책임자 둘 다 리뷰
4. CI 그린 확인 후 머지
5. 배포 후 회고에 기록 (왜 미리 못 잡았는지)
