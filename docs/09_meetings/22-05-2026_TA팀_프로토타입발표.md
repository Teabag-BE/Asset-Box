## 프로토타입 발표 이후 요구사항

### 핵심 요구사항 요약

1. 에셋 업로드 시 여러 형태의 파일을 함께 관리해야 한다.

2. 3D 에셋뿐 아니라 2D 리소스도 업로드 가능해야 한다.

3. HDRI/EXR 환경맵은 사용자가 직접 올리기보다 기본 내장 환경을 제공하는 방향이 좋다.

4. 에셋 정보에는 polygon count가 포함되면 좋다.

5. 요청 게시판에는 참고 이미지를 첨부할 수 있어야 한다.

6. 에셋은 여러 번 수정될 가능성이 높으므로 버전 관리 또는 수정 이력 관리가 필요하다.

7. S3 버전 관리와 저장 용량 비용을 고려해야 한다.

8. 3D 에셋은 웹에서 360도 회전 가능하므로 별도 시연 영상(mp4)은 필수는 아니다.

9. TA가 없는 팀도 요청 게시판을 통해 필요한 에셋을 요청할 수 있어야 한다.

10. 일부 필드는 생성 이후 수정 불가능하게 관리할 필요가 있다.  
  
위 사항에 관해서는 다음 주 26일 본 회의 때 조금 더 디벨롭 해보기로함.

### 인증 / 회원가입

- 로그인 방식은 **Form + OAuth2(Google, Naver)** 를 병행한다.
- 구현 우선순위는 **Form → Google → Naver** 순서로 둔다.
- Kakao는 이메일 매칭이 복잡해질 수 있으므로 v1에서는 예외 케이스로 보고 **Form 회원가입을 권장**한다.
- 가입 가능 여부는 **이메일 화이트리스트**로 제한한다.
- Form 회원가입 시 `realName`, `nickname`, `major`를 받는다.
- `major == null`인 사용자는 로그인 후 **내 정보 보완 페이지로 리다이렉트**하고, 보완 전까지 다른 페이지 이동을 제한한다.
- 가입 이후 일반 유저는 `realName`, `major`를 직접 수정할 수 없다. 수정은 관리자 정책 영역으로 둔다.
- Redis, 분산락은 v1 이후로 보류한다.

### 권한 / 운영

- 일반 에셋 게시글은 저작권 및 내부 공유 정책 때문에 **비회원 열람 불가**로 변경한다.
- 강한 권한이 필요한 작업, 예: 유저 삭제, 유저 제재, 권한 변경, 글 강제 삭제는 **SUPER_ADMIN/root 전용**으로 둔다.
- Admin은 일상 운영과 검토 중심으로 제한하고, 요청 게시판 흐름은 가능하면 **요청자와 Assignee 중심**으로 설계한다.

### 파일 정책

- 파일 도메인은 에셋 파일뿐 아니라 **게시글 썸네일, 프로필 이미지, 요청 게시판 참고 썸네일**까지 공통으로 관리한다.
- 파일 업로드 요청은 각 도메인 API에서 multipart로 받고, 실제 저장/검증/메타데이터 관리는 File 도메인 서비스에 위임한다.
- 파일 다운로드/이미지 조회도 로그인 사용자에게만 허용한다.
- 다운로드 로그/파일 통계는 MVP 범위에서 제외하고, 추후 Analytics/Audit 또는 운영 모니터링 범위에서 재검토한다.

### 요청 게시판 상태 흐름

상태는 5개로 통일한다.

```text
REQUESTED(요청됨) → IN_REVIEW(검토중) → IN_PROGRESS(제작중) → COMPLETED(완료)
                                      ↘ REJECTED(반려됨)
```

- 요청 수락/반려/완료/재배정 시 요청자에게 DM으로 상태 변경 알림을 보낸다.
- 요청이 `IN_PROGRESS`로 들어가면 요청자는 글을 수정할 수 없다.
- 반려된 요청은 완전 종료가 아니라, 필요하면 다시 `REQUESTED` 또는 `IN_REVIEW`로 되돌릴 수 있다.
- 한 요청에는 Assignee를 1명만 배정한다. 멀티 Assignee는 v1 범위에서 제외한다.
- 수락/반려/완료 등 중요한 액션에는 프론트에서 확인 팝업을 띄운다.

> 1. 요청 게시판 상태 흐름 정의
>   본 흐름은 다음과 같습니다. Unity, Unreal 쪽에서 에셋 요청 게시판에 요청글을 작성하면, TA분들이 해당 요청을 확인하고 수락합니다. 요청이 수락되면 한 명의 Assignee가 배정됩니다. (멀티 Assignee 불가) 요청 수락 시 요청자에게 DM으로 [요청 수락] 메시지가 전송되고, 이후 완료되거나 반려될 때도 [상태 변경] 메시지가 개인 메시지로 전송되는 구조입니다. GitHub Issue처럼, 에셋 제작이 완료되면 결과물을 업로드하면서 요청 글이 완료 상태로 변경됩니다. 요청 상태는 총 다섯 가지로 정리했습니다. 요청됨 → 검토중 → 제작중 → 완료 ↘ 반려됨 상태명 기준으로는 다음과 같습니다.
>
> - 요청됨
> - 검토중
> - 제작중
> - 완료
> - 반려됨
>
>  ⸻ 요청 게시판 관련 논의된 문제들 A. Admin 개입 범위 현재 만들어진 구조에서는 검토중, 반려됨 등 상태 변경을 Admin이 버튼을 눌러 처리할 수 있습니다. 하지만 논의 결과, 가능하면 Admin 없이 TA팀과 에셋 요청자들이 직접 처리할 수 있는 구조가 더 자연스럽다는 의견이 있었습니다. 따라서 요청 게시판의 상태 변경 권한은 Admin 중심이 아니라, 요청자와 Assignee 중심으로 다시 조정하는 방향이 좋을 것 같습니다. B. 제작중 상태에서 요청자가 내용을 수정하는 문제 제작이 이미 시작됐는데 요청자가 갑자기 글을 수정해서 요구사항을 늘리면 문제가 생길 수 있습니다. 따라서 다음과 같이 정리했습니다. 요청이 수락되어 제작중 상태로 들어가면, 요청자는 더 이상 글을 수정할 수 없도록 한다.
>
> - C. TA가 제작중 상태에서 갑자기 반려하는 문제 제작중 상태인데 TA가 마감일 직전에 반려해버리면 요청자 입장에서는 문제가 될 수 있습니다. 반대로 TA가 실수로 요청 수락 버튼을 눌렀을 수도 있고, 작업하다 보니 요청이 너무 무리라고 판단되어 반려하고 싶을 수도 있습니다. 그래서 아래와 같은 방향이 논의됐습니다.
>   - 요청 수락 또는 반려 시 확인 팝업을 한 번 더 띄운다.
>   - 노매너 유저를 제어하기 위해 유저 프로필에 제작중 반려 3회 같은 기록을 공개할 수 있는지 검토한다.
>   - 다만 실제로 작업이 어려워 반려해야 하는 상황도 있을 수 있으므로, 단순히 패널티로만 처리하기보다는 다른 Assignee를 다시 배정할 수 있는 흐름이 필요하다.
>    D. 반려된 요청글 처리 방식 현재 기본 구조에서는 반려 버튼을 누르면 해당 글이 완전히 반려 상태가 되고, 이후 삭제나 수정이 불가능합니다. 이 경우 요청자가 새 요청글을 다시 작성해야 합니다. 하지만 이 방식은 사용자 경험이 좋지 않을 수 있기 때문에, 다음과 같이 수정하는 방향이 논의됐습니다. 반려된 요청은 완전히 종료시키기보다, 다시 Assignee 배정 단계 또는 요청중 상태로 되돌릴 수 있게 한다. ⸻
>   1. Super Admin / Admin 구조
>     재는 Super Admin 1명이 Admin을 배정하는 구조입니다. 이 부분은 다음과 같이 정리했습니다. root 계정을 Super Admin으로 두고, 유저 제재, 유저 삭제, 글 삭제 등 강한 권한이 필요한 경우에만 Super Admin으로 로그인해서 처리한다. ⸻ 기타 논의된 내용 추가로 아래 내용들도 논의됐습니다.
>   - 로그인 시 전공 == null이면 내 정보 수정 페이지로 이동
>   - 전공 정보가 입력되기 전까지 다른 페이지 이동 제한
>   - User 필수 정보는 이름, 실명, 전공으로 정의
>   - Form 회원가입 시 실명과 전공을 받기
>   - 가입 이후에는 이름과 전공 수정 권한을 일반 유저에게 주지 않기
>   - 에셋 요청 시 참고용 썸네일을 업로드할 수 있는 칸 추가
